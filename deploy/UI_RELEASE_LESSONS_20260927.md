# 美工发布问题与执行约定（2026-09-27）

## 用户要求

美工需要频繁发布，不接受把普通界面修改变成漫长整包发布。遇到问题要定位、修复、继续，不要形成“失败—回滚—原样重发”的循环；不要重复已通过且输入未变的检查。

## 本次确认的原因

1. `scripts/ci-impact.mjs` 的 `frontendOnly` 将整个 `src/client-plugins/two-factor/` 和 `two-factor-tool/` 排除在前台发布之外。实际调用分类器，普通布局 CSS 返回 `frontend`，`two-factor-page.css` 与 `two-factor-page.tsx` 均返回 `runtime`，但后者的业务包、数据库检查列表仍为空。因此，整包分流并不表示这次美工修改涉及后端或数据库。
2. 商城构建同时输出 `dist` 与 `dist-two-factor`，独立工具复用商城 2FA 组件。`.github/workflows/deploy_frontends.yml` 当前只复制 `dist`；runtime artifact 打包另包含 `dist-two-factor`。这个产物覆盖缺口与整个目录的限制有关；限制设得过宽，发布前又未先解决，导致本次纯界面工作走了整包部署。不能直接删掉限制后声称所有独立页面都已更新。
3. 首次发布的生产健康检查报 `restore-drill-missing-or-stale` 并自动回滚。部署前没有充分校验恢复演练凭据新鲜度；健康检查还使用服务启动时的时间判断后续才读到的凭据。失败日志证实凭据检查阻断，但没有证实具体时间竞态就是这次生产故障的唯一原因。

## 后续执行规则

1. 发布前先核对实际分流与完整差异；纯界面变更原则上只发布必要的前台产物。检测到 2FA 目录限制时先解决产物/分流问题，不直接再启动整包发布。
2. 只运行改动页面或组件的必要检查；复用输入一致的成功检查和构建产物。通过的步骤不反复运行，失败后只补失败项及直接依赖。
3. 外观问题优先前向修复；切换前失败保留现网、修复后继续。回滚无法消除根因；若确实需要恢复网站可用性，只将恢复服务作为临时保护，随后定位根因、修复、用新 SHA 完成受影响检查后继续。禁止未修复就再次执行同样的失败步骤。
4. 2FA 快速发布需覆盖主商城与适用的独立工具产物、指针和实际服务路径。只去掉分类器限制会留下独立页面不更新的风险，不能作为完整修复。
5. 分开报告测试、构建、打包、恢复验证、切换、页面验收的耗时；队列或阻断要及时告知，不以不断轮询或重发代替诊断。
