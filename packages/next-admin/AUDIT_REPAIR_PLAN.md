## 一、目标与执行边界

- 以中国电商运营人员的高频任务为中心，减少菜单层级、重复入口和来回跳页。
- 列表、筛选、批量处理和同一对象的辅助设置优先合并；创建/编辑、履约、退款、密钥等高风险或长流程保留独立工作区。
- 所有业务数据必须来自真实 GraphQL/HTTP 接口。后端没有能力时明确列为后端任务，不制作只能展示、不能工作的假页面。
- 删除、退款、改密、密钥、余额调整、提现审批等敏感操作必须具备权限校验、二次确认、明确结果反馈和审计依据。
- 本方案不授权新增大型依赖、升级框架、改数据库、提交 Git、部署或修改生产环境。

## 二、当前结论

### 2.1 页面架构结论

现有 8 个一级分类和任务型页面合并方向总体合理，不需要恢复 Gemini 最初拆出的全部独立页面。

| 原规划能力                                         | 当前入口                                                 | 处理结论                                             |
| -------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- |
| SPU、SKU、分类、规格、筛选属性、素材               | 商品列表、商品编辑、分类与属性、库存与仓库、卡密、素材库 | 保持现状；SKU 跨商品运营放库存页，规格与属性放分类页 |
| 订单、履约、发货、退款、售后、评价                 | 订单列表、订单详情、售后与退款、评价管理                 | 保持现状；待发货是订单筛选，发货和退款留在订单详情   |
| 优惠券、秒杀、ROI                                  | 优惠与促销                                               | 合并合理，用标签页区分任务                           |
| 分销规则、推广员、佣金、流水、提现、海报           | 分销与返利                                               | 合并合理，用标签页区分任务                           |
| 商城装修、楼层区块                                 | 商城装修                                                 | 合并合理，楼层编辑使用抽屉或二级编辑器               |
| 公告、法律内容、推广落地页                         | 内容与页面                                               | 合并合理                                             |
| 多店铺、商家主体、支付、配送、域名、税率、基础设置 | 店铺综合设置                                             | 合并合理；库存点仍放库存与仓库                       |
| 成员、角色、权限                                   | 员工与权限                                               | 合并合理                                             |
| Job Queue、定时任务、配置仓库、API 密钥、健康状态  | 系统运维                                                 | 合并合理，仅超管可见                                 |

客户管理虽然不在最初清单中，但属于 Vendure 核心运营能力，应保留。AI 服务商密钥接入从运营设置中单独拆出也合理，可以避免普通运营人员接触平台级密钥。

不应继续保留或新增的伪页面：管理员登录 TOTP/恢复码、CPU/内存/数据库连接池趋势。第三方 TOTP 动态码工具已有独立后端能力，不属于登录 2FA。

## 三、按优先级执行

## P0：恢复稳定基线

### P0-1 收尾分销海报素材选择器

- 完成 `PosterEditor` 的远程素材搜索，不再依赖父页面一次读取固定数量素材。
- 保留当前已选择的旧素材，即使它不在当前搜索结果中也必须能显示、预览和保存。
- 增加加载、错误、空结果和匹配总数提示。
- 修复当前 `assets` 属性缺失导致的 TypeScript 构建错误。

验收：`bun run build`、`bun run lint`、`bun run test` 全部通过且 lint 无新增警告。

### P0-2 清理 3 个 Hooks 警告

- 处理员工与权限、店铺综合设置中的 `fetchMore` effect 依赖。
- 防止重复请求、并发分页、切换 Channel 后混入旧 Channel 数据。
- 不使用简单关闭 lint 规则掩盖真实生命周期问题。

验收：lint 0 error、0 warning；分页合并按 ID 去重。

### P0-3 固化构建门禁

- 每一批修改结束都运行前端 test、lint、build。
- 同时保留首次改密后端测试和会话响应头测试。
- 在 P0 全绿前，不开始大文件拆分或视觉重构。

## P1：消除“数据存在但运营人员看不到”的缺陷

### P1-1 主列表必须服务端分页

- AI 生图任务：增加状态筛选、服务端分页和总数。
- API 密钥：增加服务端分页，不再固定读取前 200 条。
- 客户分组：列表与选择器改为服务端搜索/分页，保留已选分组。
- 库存点：仓库列表或选择器支持完整读取，不能停在前 100 条。

### P1-2 辅助选择器必须远程搜索

- 客户、商品、SKU、分类、素材、渠道等选择器统一为“输入关键词后查询”，并保留已选项。
- 客户端插件的指定分类选择不能只在前 200 个分类中本地搜索。
- 商品渠道和登录渠道不能静默截断在 200 条；小数据集可分批完整读取，大数据集使用远程搜索。
- 搜索文案必须说明搜索范围，例如“按名称搜索全部商品”，不能把“当前页过滤”伪装成全量搜索。

### P1-3 历史记录要么分页，要么明确边界

- 客户订单历史、订单状态历史、系统近期任务如果只展示最近 100 条，界面必须明确写“最近 100 条”。
- 需要完整追溯的业务记录增加分页；纯诊断性的近期记录可保留有限窗口。

验收：准备超过 200 条分类/商品/客户、超过 100 条库存点/分组、超过 50 条 AI 任务的数据，最后一条仍能被搜索、选择或翻页找到。

## P2：核心业务闭环回归

### P2-1 账号、权限与多店铺

- 登录、Token 失效、首次强制改密、个人修改密码、退出登录完整回归。
- 超管页面除菜单隐藏外，还必须由路由和后端权限共同保护。
- 切换 Channel 后清空页签和 Apollo 缓存，商品、订单、库存、营销和店铺设置全部显示新 Channel 数据。
- 敏感 mutation 逐项确认当前管理员密码保护和后端权限。

### P2-2 商品与库存

- 新建/编辑商品，验证中文源内容、主图/详情图、分类、规格组合、SKU、渠道归属、渠道价格和库存。
- 批量启停、批量调价、库存点调整、卡密导入和自动发货配置要有部分失败反馈，不能只显示笼统“成功”。
- 离开未保存商品或复杂编辑器时增加未保存提醒。

### P2-3 订单、履约与售后

- 订单搜索、待发货筛选、拆分发货、物流单号、退款、内部备注、售后审核和评价回复逐条回归。
- 状态机操作只展示当前订单允许的动作，后端拒绝时保留上下文并给出可理解原因。
- 金额、币种、时区和中文状态文案统一。

### P2-4 营销、装修与插件

- 优惠券、秒杀、ROI、分销规则、推广员、佣金、提现和海报全部使用真实接口。
- 时间状态持续刷新；跨时区的开始/结束时间按店铺配置解释。
- 装修区块、公告、落地页和客户端插件保存前做必填与冲突校验。
- AI 密钥只允许超管操作，前端不回显完整密钥，日志和错误中不得泄露。

验收：每个核心流程至少覆盖成功、校验失败、接口失败、空数据和无权限 5 类状态。

## P3：设计完整性与中国后台操作习惯

### P3-1 信息层级

- 一级菜单固定为工作台、商品、订单与售后、客户、营销、店铺、插件与服务、系统与权限。
- 列表页统一采用“标题与主要操作 → 搜索/筛选 → 批量操作 → 数据表格 → 分页”。
- 编辑页统一采用清楚的分区/标签、底部或顶部固定保存区、离开提醒和明确保存状态。
- 标签页只承载同一业务对象的并列任务，不把完全不同的角色任务硬塞进一个页面。

### P3-2 交互一致性

- 所有弹窗、抽屉统一 Escape 关闭、焦点锁定、关闭后焦点返回；提交中禁止误关闭。
- 删除、退款、提现、密钥删除、余额调整使用危险操作确认；普通保存不重复确认。
- 成功反馈指出影响对象；失败反馈保留表单内容并提供重试。
- 图标按钮有可访问名称，表单错误与字段关联，加载和异步状态可被辅助技术识别。

### P3-3 响应式与视觉验收

- 桌面重点检查 1440px 和 1280px；移动端重点检查侧边栏、表格替代布局、抽屉和表单，不要求把复杂运营表格强行压成不可读卡片。
- 检查横向溢出、遮挡、裁切、留白、字号、对比度、按钮目标尺寸和键盘顺序。
- 登录态视觉审计必须使用当前运行页面重新截图，不能用旧截图代替最终验收证据。

验收：主要流程逐步截图，逐图记录页面健康、UX 问题和可访问性风险；仅凭截图不能确认的键盘、屏幕阅读器和接口行为单独实测。

- 增加失败次数限制、冷却时间和超管恢复流程。

### P4-2 管理后台用户 2FA 动态码工具（已实现）

- 已完成按管理员隔离、AES-256-GCM 加密存储、重复密钥防护、100 个账号上限、批量导入和删除流程。
- `next-admin` 使用 `/plugins/two-factor-codes`，并保留 `/two-factor-codes` 旧地址跳转；不要再次因登录 2FA 尚未实现而移除此工具。

### P4-3 系统监控

- 审计报告记录每个流程步骤、页面健康、截图证据和无法仅凭截图确认的限制。

## 六、完成定义

只有同时满足以下条件，才能把新管理后台标记为“设计和功能已完成”：

- 页面架构与上述合并决策一致，没有重复入口和后端不支持的假页面。
- P0～P3 全部验收通过，构建、lint、测试为绿色。
- 超过固定阈值的数据仍能被查找和操作。
- 核心业务成功/失败/空状态/无权限均有明确体验。
- 真实登录态桌面与移动端回归通过，并保留本轮截图和问题记录。
- 后端未完成的 P4 能力明确标记为阻塞，不计入前端交付完成率。
