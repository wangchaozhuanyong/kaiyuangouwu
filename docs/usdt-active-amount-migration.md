# USDT 活动金额占用迁移与回退

本改动已在独立 SQL.js、MySQL 8.0、PostgreSQL 16 测试库演练。本文规定上线与回退约束。具体生产执行结果必须以对应提交的发布记录和工作流证据为准。

## 数据与行为

- 新增可空的 `activeMatchKey` 和唯一索引，活动占用跨 Channel 共享同一钱包与精确金额范围。
- `matchKey` 保留为历史查询索引。报价、订单、付款和交易历史不删除；`quoteId`、`transactionId` 的唯一约束保留。
- 回收需要完整扫描、报价到期及 30 分钟发现宽限。分页截断、扫描失败、确认未完成时继续占用。
- 复用过的金额发生到账时，单凭金额、地址和时间不能证明订单归属，进入 `MANUAL_REVIEW`，保留交易唯一归属与占用，不自动支付或交付。人工复核仍需业务人员处理；本改动没有新增人工打款或解锁接口。
- 金额复用增加人工复核量，不构成长久全自动收款保证。

## 两阶段迁移

1. `AddUsdtActiveAmountKey1788703200000`：增加列、保守回填全部旧占用、建立活动唯一索引，保留历史唯一索引。
2. `ReleaseUsdtHistoricalAmountKeys1788706800000`：确认活动唯一索引存在，补齐两阶段之间旧程序写入的空活动键，再将历史唯一索引改成普通索引。已经完成取消唯一性后重跑不会重新占用历史金额。

第二阶段必须在所有旧 API 与 worker 写入停止后执行。新版本在阶段一也受原历史唯一约束限制，不应把这段时间宣称为容量问题已经解除。

## 发布窗口

1. 另外确认生产数据库引擎/版本、应用制品、完整待执行迁移清单、备份与恢复点，并记录各状态行数、报价/订单/交易关联和当前索引。已有待执行的其他迁移也必须单独核对。
2. 在隔离副本演练阶段一；确认新代码双写时历史唯一约束仍生效。分阶段发布须由发布流程明确限制本轮迁移列表。
3. 在批准的维护窗口停止旧 API 与 worker 的报价分配、扫描和结算写入；确认进程/实例已经停止。仅替换 API 或仅停队列不够。
4. 执行阶段二，再启动使用同一新版制品的 API 和 worker。先核对列和索引、旧记录数量及交易关联，再恢复报价与扫描。由正常扫描逐步回收，不手工清空活动键。
5. 验收首次金额、已回收金额、相同报价重试、人工复核通知、Shop API 状态及真实客户端文案；核对金额与交易关联后再恢复全部流量。

注意：两个迁移都注册在 `packages/dev-server/migrations/index.ts`。通用 `runMigrations(devConfig)` 会执行全部待执行迁移，不会在两个阶段之间自动暂停。因此，直接使用现有启动迁移流程时必须先停止全部旧写入者，再在同一维护窗口执行两阶段。不要把普通滚动重启当成分阶段发布。

当前启动规则来自 `packages/dev-server/runtime-flags.ts`：生产只有 `RUN_MIGRATIONS=true` 才执行迁移；非生产默认执行，只有 `RUN_MIGRATIONS=false` 跳过。仅做代码验证时不要启动连向业务库的服务；本轮使用独立测试库。

## 自动发布保护

`deploy/deploy-production-from-s3.sh` 在候选制品校验与生产环境检查后执行 `usdt-migration-guard.cjs plan`。它从当前受审迁移注册表与生产 MySQL 8 的迁移记录计算待执行列表；本次只允许上述两条迁移，额外待执行迁移必须另外审核。输出只包含数据库版本、迁移名、索引状态、行数、状态计数、关联计数与历史摘要，不输出钱包、客户或交易标识。

随后停止并持久保存 API、worker 的 PM2 状态，确认两者无存活 PID，保存迁移前摘要，完成本地和异地备份，再执行通用迁移入口。迁移后在进程仍停止时，核对历史字段摘要完全一致、旧占用已回填、报价/交易唯一约束完整、历史索引已取消唯一性，才启动新 API 与 worker。

所有运行时切换（包括自动回滚和恢复）都在修改 PM2 前检查实际数据库结构与候选制品的活动占用能力。历史唯一约束已取消时，自动回滚到旧程序会输出 `ROLLBACK_BLOCKED_USDT_SCHEMA` 并保持写入停止，不会删除数据或自动回退结构。需要使用兼容新结构的修复制品恢复服务，不能把失败的回滚描述为恢复成功。

## 回退

- 尚未实际复用：停写并确认没有重复历史键后，先回退阶段二（恢复历史唯一索引），再回退阶段一（删除活动列）；三个测试引擎均已演练。
- 已实际复用：阶段二的 `down()` 主动拒绝创建不可能成立的历史唯一索引，阶段一也拒绝直接删除活动列。保留历史与交易，使用兼容新结构的程序回退或前向修复。
- 不可为通过回退而删除付款记录、交易或重复历史键。恢复备份前必须对账备份之后的新交易。
- 异常期间优先停止新报价，保留使用兼容版本的扫描与审计能力；不得重新启动不认识活动占用语义的旧 worker。

## 已执行的隔离验证

- SQL.js：迁移重跑、历史/交易/报价约束、两阶段之间旧写入、未复用回退、复用后拒绝回退。
- MySQL 8.0 与 PostgreSQL 16：上述迁移测试，以及同报价并发、跨 Channel 共钱包并发、双 worker 入账一次、999 个历史占用回收后继续报价。
- 链接口使用受控测试数据；未向真实链发送交易，也未执行真实收款或生产验收。
