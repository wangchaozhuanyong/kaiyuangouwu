# 网站设计与交互治理方案

状态：2026-11-01 当前规则。适用本仓库商城、管理后台、新路由、组件、弹窗和插件。此文件是设计工作的统一入口与职责索引，具体数值和行为只在下表对应的规范中维护。

## 一、先解决机制，再接入页面

| 根因与已确认问题 | 统一修复位置 | 防止再次出现的约束 | 验收依据 |
| --- | --- | --- | --- |
| 页面保存第二份业务缓存，返利配置恢复无时限旧值 | 商城根 QueryClient；后台 Apollo 与公共查询适配器 | 服务端数据只设一个真源；草稿、图片呈现元数据、传输去重不能冒充业务缓存 | 实际查询客户端的缓存、作用域、失效和会话清理测试 |
| 刷新不读真实列表、重复读取、隐藏或离线仍轮询 | 公共刷新入口、查询库轮询与活动状态 | 相同读取合并；刷新只读；手动计费诊断只在用户显式操作时运行 | 连续刷新、历史变化、隐藏/离线/恢复与局部失败 |
| 同账号更新、换语言或 A→B→A 解除提交锁定 | 所属业务的共享写操作所有者 | 新操作先确定存活范围；离页不代表取消已发出的写入；未知结果重试沿用原标识 | 真实挂载/卸载、迟到回执、跨账号隔离、同参数显式重试 |
| 后台失败隐藏余额，或把读回失败说成保存失败 | 公共读取状态与反馈组件 | 区分首读、有效旧数据、空结果、后台失败、写入成功后读取失败 | 刷新失败保留值、只读重试不触发写入 |
| 文档和 React 加载界面重叠；页面各写入场动画 | 文档接管、PageReadinessBoundary、共享正文动效控制器 | 同一目标只有一个等待反馈所有者；刷新不重播；固定控件与主图不参与正文入场 | 冷启动逐帧、快速导航、缓存返回、减少动态效果 |
| 历史规则仍指导新开发；新增页面漏分类或漏门禁 | 本索引、包级 AGENTS、现有交互门禁和构建验收 | 按职责替换旧规则；自动扫描新目录；路由文件、路由注册和页面分类对齐 | 负例规则测试、全源扫描、路由契约、构建验收入口测试 |

前述业务机制已在上一轮本地实现并验证。本轮收口规范和准入门禁，不另起页面实现。代码完成、本地验收、生产发布与真实业务结果分开记录。

## 二、规则所有权

| 关注点 | 唯一维护位置 | 其他文档的处理方式 |
| --- | --- | --- |
| 项目边界、多店共用、授权与发布 | [仓库 AGENTS](../AGENTS.md) | 继续遵守，不被设计任务扩大授权 |
| 商城加载、缓存、刷新、导航、写入生命周期、正文动效 | [商城交互标准](../packages/storefront/LOADING_REFRESH_INTERACTION_STANDARD.md) | 视觉契约只引用，不再复制时长或状态方案 |
| 商城已确认布局、皮肤与组件外观 | [视觉契约](../packages/storefront/DESKTOP_SKIN_DESIGN_CONTRACT.md) | 按当前有效索引与明确替代关系读取，不能恢复已退役方案 |
| 商城字体角色与度量 | [排版标准](../packages/storefront/TYPOGRAPHY.md) 与 `src/styles/typography.css` | 页面只消费现有角色 |
| 后台读取、刷新、草稿、控件、反馈与布局 | [后台交互标准](../packages/next-admin/LOADING_REFRESH_INTERACTION_STANDARD.md) | 沿用后台框架；两端行为一致，会话和查询缓存分别管理 |
| 新功能具体接入与检查命令 | 各包 [商城 AGENTS](../packages/storefront/AGENTS.md)、[后台 AGENTS](../packages/next-admin/AGENTS.md) | 作为接入索引，不复制另一套设计方案 |

历史 QA、发布记录、旧截图与备份只证明当时的候选，不能覆盖当前规范或作为新页面验收通过的依据。修改某项规则时直接更新其唯一维护位置、调用方和相关门禁；不在其他文件追加相反规则。当前用户要求优先；未涉及的已确认布局、商家图片和业务规则继续保留。

## 三、新增与改版准入

实现前在本次任务中明确以下内容，不要求每个小修改另写一份文档：

1. 路由或宿主、页面族、业务目标与唯一主操作。商城新增路由同步接入 `storefrontRouteNames`、文件路由、`desktopPageFamilyByRoute`；后台沿用现有工作区。
2. 读取身份、作用域与唯一数据所有者；首次缺失、成功空值、缓存返回、后台刷新、局部失败、离线及会话变更的表现。
3. 写入确认、幂等与冲突范围、离页后的存活及读回归属。普通按钮的局部 busy 不能承担跨页仍在进行的操作；不把图片工坊的专用适配器复制给其他业务。
4. 草稿与服务端数据分开；后台更新不能覆盖输入，退出账号不能恢复上一账号结果。需要显式授权或可能计费的读取不参加自动聚焦、联网重试。
5. 使用现有页面壳、控件、Overlay、图片和语义 token。公共能力缺失时先完善既有公共所有者，再让受影响页面接入；不能在页面 CSS、内联样式或新 Hook 中另造同类规则。

普通展示、弹窗、表单、列表、轮播的职责不同，不要求所有状态使用同一个动画。相同职责复用同一所有者；任何局部动效都不能承担就绪判断、数据缓存或提交锁定。

## 四、按影响执行门禁

| 改动 | 必须执行 |
| --- | --- |
| 纯规范或规则检查器 | 相关规则负例测试、全源扫描、文档链接与既有构建验收入口检查 |
| 商城页面、样式或运行时代码 | `bun run check:interaction`、受影响测试与既有构建；按影响执行排版、多店及皮肤检查 |
| 后台页面、样式或运行时代码 | `bun run check:feedback`、受影响测试与既有构建 |
| 加载、导航、刷新或可见交互 | 用实际组件验证受影响场景；包括手机/桌面、中英文、两套皮肤及减少动态效果中的相关组合 |
| 查询或写入生命周期 | 使用实际根查询客户端验证去重、作用域、挂载/卸载、迟到结果与清理；mock 不能代替这些验证 |

商城构建继续调用现有 `scripts/verify-production-build.mjs`，该验收入口强制执行同一个交互门禁；后台构建已有 `check:feedback`。新增源目录自动进入扫描，不依赖开发者手工把新页面列入扫描名单。路由覆盖从实际注册与文件清单比较，不硬编码“共多少页”。

门禁拒绝已知违规，运行时测试验证异步状态，浏览器验证真实呈现。三者共同形成准入条件。不能为通过检查扩大例外、抬高资源预算或删除断言。静态分析不能证明任意间接调用的全部语义，新机制仍需上述行为证据。

## 五、例外与完成标准

例外必须限定真实所有者、原因、触发条件、数据范围、清理时机与回归场景；只对实际缺口使用。SSR 每文档缓存、敏感凭据短存、文档版本恢复、公开发布回查及本地视觉时钟保持既有职责，不能被业务页复制为第二套机制。

本轮完成标准：旧加载冲突从活动规则移除；根与包级入口指向当前规范；构建验收无法跳过已知违规；新路由漏注册/分类能失败；定向检查通过并记录证据。发布和生产验收继续遵守既有授权。后续修改须满足同一准入条件，发现新的缺陷模式时扩展既有公共机制和门禁。
