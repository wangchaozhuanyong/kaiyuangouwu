# 分类持续同步：迁移与恢复说明

本说明对应本地候选，不代表生产迁移或启用授权。开发于 2026-10-15 开始，收尾验证跨至 2026-10-16（Asia/Kuala_Lumpur）。

## 数据变更

迁移 `AddCatalogContinuousSync1792022400000` 已登记在 `packages/dev-server/migrations/index.ts`，只新增三张表：

| 表 | 用途 | 默认行为 |
| --- | --- | --- |
| catalog_sync_rule | 来源、分类、目标、执行账号、版本、水位、游标和 Worker 租约 | enabled=false，state=DISABLED |
| catalog_sync_binding | 按规则记录商品、分类、配送映射及接管前基线 | PENDING，不复制库存和卡密 |
| catalog_supply_snapshot | 订单行原始供货店铺、规则版本与报价依据 | 结账预占时写入；已接受订单不再改写 |

既有商品、订单、库存表不迁移、不清理。没有新环境变量或新运行依赖。文件版本继续保存在现有 `DigitalOrderReservation.fileVersionId`；供货快照保存来源身份和金额依据，包装、批次及文件记录沿用原有履约记录。

重复执行 up 会保留已存在的表及履约历史。down 明确拒绝删表：已接受订单可能仍引用来源快照，不能用删除表的方式回退。

## 发布时的顺序（本轮未执行）

1. 核对最终候选、生产继承版本和数据库备份；使用仓库原有迁移发布流程执行新增迁移。
2. API 与 Worker 使用同一份支持供货快照的版本，再发布后台和商城。保持全部规则关闭。
3. 确认 Worker 队列 `catalog-continuous-sync`、定时任务 `reconcile-catalog-continuous-sync` 正常运行。
4. 在隔离环境完成验证后，由平台商品管理人员为一个具体经营店铺及分类生成预览。核对接管差异、目标经营模式、固定汇率、配送范围及交付就绪项。
5. 实际启用属于独立生产数据写入，按另外取得的授权执行，并核对逐项目标状态。按钮“操作已受理”不等于全部同步完成。

## 状态与恢复

- COMPLETE：本次扫描结束且无记录的待处理错误；以 completedGeneration 和当前 generation 是否追平判断事件是否全部处理。
- PARTIAL：部分商品待配置或失败；后台可分页查看原因。修复来源条件后“重新对账／续做失败项”；不需要删除规则重建。
- 每项成功记录保存指纹；不变项跳过写入。发现目标价格或规格分配漂移时修复投影。
- 每个 Worker 页面最多处理 100 个商品。游标记录已完成页，runGeneration 固定整次扫描的事件水位；扫描期间的新事件触发下一次从头核对。
- 60 秒租约配合唯一 token 防止旧 Worker 覆写新执行者。过期后可恢复，正常每项执行会续租。
- 每五分钟按规则 ID 游标补偿扫描；任务启动时也核对开启规则。超过单次扫描上限时，下一轮沿扫描游标继续。
- 暂停或执行账号失权会停止新的供货购买。历史订单继续依据来源、预占及文件版本履约。

## 恢复边界

先暂停规则并保留新表、订单快照、预占、卡密发放及库存流水；排查后优先向前修复。已经接单后，不能直接退回不识别来源快照的旧后端，否则可能按销售店铺释放或回补库存。需要兼容恢复版本并复核未完成订单。

目标分类按映射建立，退出范围后隐藏受管分类；不删除原有分类和历史订单。最后一条有效规则退出商品范围时恢复接管前的独立授权及价格基线；规则暂停本身用于暂停受管销售，不等于解除接管并恢复独立经营。

## 验证边界

SQL.js 已实际验证创建、默认关闭、重复 up 与 down 的历史保护。MySQL 在独立无生产数据的测试数据库中先执行真实 up，再启动 ORM 与业务测试；覆盖建表、默认值、重复 up。PostgreSQL 分支有兼容实现，本轮未启动 PostgreSQL 实例验证。
