## 数据表设计检查

核心结构方向合理，金额采用最小货币单位和独立 currencyCode；业务记录带 channelId。账户、关系、奖励、钱包、流水、余额使用、通用钱包预占和提款均有实体与对应迁移来源。

| 表                      | 已有关键约束                                                                |
| ----------------------- | --------------------------------------------------------------------------- |
| referral_program_config | 每个 Channel 唯一配置，配置版本冲突校验                                     |
| referral_account        | channelId + customerId 唯一；channelId + inviteCode 唯一                    |
| referral_relationship   | channelId + inviteeCustomerId 唯一；保留邀请码快照、来源与绑定/首次成交时间 |
| referral_reward         | channelId + orderId 唯一；保留比例、有效金额、释放、累计扣回及退款快照      |
| referral_wallet         | referralAccountId + currencyCode 唯一；三个余额桶；版本字段                 |
| referral_ledger_entry   | idempotencyKey 唯一；三个变动与事后余额、操作者及业务关联                   |
| referral_balance_use    | channelId + orderId 唯一；抵扣与退款累计值；本次修复事件回执与累计值推进    |
| referral_wallet_usage   | 幂等键唯一；channelId + resourceType + resourceId 唯一；预占/结算/释放      |
| referral_withdrawal     | code 唯一；状态时间、金额币种、脱敏收款信息、管理员与外部流水号             |

另外有两项结构加固事项，尚未证实造成实际数据异常：

- 金融相关表对 Channel、Customer、Wallet、Order 等使用 CASCADE。若这些实体发生数据库硬删除，可能连同返利、流水及提款证据一起删除；不能把普通软删除等同于已发生该问题。应在明确数据保留政策后评估 RESTRICT 或受控归档。
- 部分表同时存 channelId/customerId/accountId/walletId，但外键主要逐列校验实体存在，未用复合约束保证这些归属字段相互一致；余额/金额的若干不变量主要依赖服务校验。可先做只读数据核对，再决定是否追加数据库约束，不能直接凭源码修改历史数据。

推广员团队还有一个口径需注意：当前从邀请关系汇总，拥有邀请码但尚未邀请任何人的账户不显示。独立 SQL.js 样例里 4 个账户仅显示 3 个有邀请者。这符合现有“按邀请码汇总邀请人数”实现；如果产品要求显示全部推广员，需要以账户表为主体 LEFT JOIN。
