# GPT 自助充值插件接入说明

## 已实现范围

商城共用页面为 `/gpt-recharge`，提交与查询采用左侧操作、右侧原任务进度的布局。Plus、Pro100、Pro200 分别对应 `plus`、`pro_5x`、`pro_20x`；Pro500 为禁用展示项。实际套餐取兑换码绑定结果，公开提交接口不接受套餐参数。

浏览器通过商城 Shop API 完成配置、验码、提交、兑换码查询和任务查询，并通过同域私有进度流读取原任务变化。Vendure 转接 ID 系统的专用服务接口。商城保存私有连接配置和不含原始兑换码／会话的交易回执；ID 系统保留兑换码及执行任务。

## 2026-11-16 进度与布局改版（本地实现，未发布）

提交页和查询页共用右侧进度面板及 TanStack Query 任务缓存。电脑端左侧为表单、完整邮箱、套餐和查询编号，右侧为当前状态及八步时间线；手机依次呈现表单、进度和任务资料。进度不设嵌套滚动区。查询页的一键粘贴只填入兑换码，不自动查询或提交。

正常连接使用 `POST /storefront-realtime/recharge-events` 接收原任务快照，任务凭证放在请求体。ID 原任务持久化提交后按业务版本通知订阅方；心跳不改变业务时间。断线重连并降频回查（5／15／30 秒，待核对 60 秒）；隐藏页面和离线时暂停，终态停止。手动“核对进度”只读同一任务，后台更新不反复转动按钮，不重提充值。

沿用网站不透明任务编号、店铺归属及凭证校验。保留原 `stage` 白名单作为兼容回退，新增 `progress` 固定白名单快照随既有加密回执保存。按任务尝试、执行次数和业务版本过滤重复／迟到事件；内部重试清除受影响的后续步骤。旧任务缺失记录时明确显示未记录，不推断已经完成。

### 对客八步与证据

| 对客步骤 | 必须取得的原始证据 |
| --- | --- |
| 任务已受理 | 原任务已持久化受理 |
| 正在验证账号／账号验证通过 | 同任务、同次执行的登录开始／成功记录 |
| 正在打开充值页面／充值页面已打开 | 实际打开记录；取得链接不算已打开 |
| 正在填写银行卡资料／银行卡资料已填写 | 整体填卡完成，或同次填写的卡号、有效期、安全码均完成；只展示状态 |
| 正在填写账单地址／账单地址已填写 | 地址填写开始／完成记录 |
| 正在执行充值／已提交，等待处理结果／付款已确认 | 分别对应提交尝试、实际提交和原执行器确认付款，不能混为成功 |
| 正在确认订阅／订阅已确认 | 原执行器订阅核对证据；缺失完成证据时不补画完成 |
| 充值成功／本次未完成／结果待核对 | 原任务权威结果；断线不能当作充值失败 |

ID 外围采集器复用管理侧已有步骤解析，只读取匹配原任务的管理详情并映射固定白名单。不展示卡号、地址值、代理、验证码、Session、原始日志或支付链接，不按时间或百分比点亮步骤。未改动固定版本充值核心及付款／重试规则。邮箱在 ID 和 Vendure 的现有持久化边界内加密保存，仅向持有效任务凭证的所属店铺返回完整邮箱。

本地验收使用合成资料，覆盖真实 ID 任务桥、Vendure 加密回执和私有进度流、合作方归属边界、界面更新与终态停止、桌面／手机布局、中英文和两套皮肤。此结果不能代替线上或真实付款验收。两端及代理配置需要配套发布；当前未推送、未部署。记录见 `outputs/recharge-live-progress-20261116/REPORT.md`。

## 服务端配置（需要正式发布后配置）

### 合作方 API

在「GPT 自助充值」为当前店铺填写 ID 系统发放的 HTTPS API 地址和「合作方 API 密钥」，并按既有规则启用前台入口。现有店铺的「原商城服务凭证」继续服务旧兑换码。合作方发放的 `RA-` 兑换码走 ID 系统 `/api/recharge/v1` 接口。商城前台生成并打开 ID 客户授权链接，账号授权在 ID 页面提交，商城从 ID 读取同一请求的进度。新配置复用原店铺加密凭证字段和回执表，原有允许列表和店铺归属校验均适用。

### 现有商城通道

1. Vendure 服务端通过现有密钥管理流程配置 `GPT_RECHARGE_ENCRYPTION_KEY`（32 字节十六进制密钥）及 `GPT_RECHARGE_ALLOWED_ORIGINS`（准确 HTTPS origin 列表）。密钥需稳定保存；已有回执时不可直接轮换或丢失。
2. ID 系统服务端配置独立的 `ONLINE_RECHARGE_VENDURE_KEY` 和准确来源地址列表 `ONLINE_RECHARGE_VENDURE_SOURCE_IPS`。来源地址是可信代理处理后的 Vendure 出口地址，不能填终端用户地址或放开任意来源。
3. 在商城超级管理员的“GPT自助充值”配置中，针对指定店铺填写允许列表中的服务地址及独立服务凭证，开启服务。配置带版本校验，服务凭证不会回显，更新后清空输入框。
4. 在当前店铺的客户端插件中启用并发布 `gpt-recharge-entry`。后台连接开启与已发布入口均满足后，才允许验码及新提交。首期只配置指定自营店；默认其他店铺关闭。
5. 使用项目正式迁移流程应用 `1792152000000-add-gpt-recharge`；不得使用同步建表替代正式迁移。本任务没有连接或迁移生产数据库。

执行地址、服务凭证和加密密钥不得进入前台环境变量、公开装修配置、页面文案或统计上报。示例文件只保留占位项。未在本文记录真实地址、凭证或客户资料。

## 店铺、任务与重试边界

- 同一执行源中的兑换码在首次受理／任务关联时归属店铺。HMAC 生成的不透明网站编号由数据库唯一索引跨店铺原子占用；其他店铺不能验证、查询或提交已关联的兑换码。
- 未使用且未分配的兑换码仍是持有码。首期按约定仅开放指定店铺；若未来要求购买时就绑定店铺，需另做发行端归属配置，不能把首次关联当作销售归属验证。
- 网站任务读取同时验证店铺归属和网站凭证。执行端编号／任务令牌加密保存，绝不直接返回浏览器。
- 并发点击只允许一次执行转发；提交前先查询原兑换码。断网或响应丢失后，回执持续保留待核对锁，不自动重提。
- 只有执行前校验拒绝，或任务创建事务明确回滚时，才允许返回“未受理”并重试。已受理后的映射异常、通信异常及结果读取异常均不能据异常类型释放提交锁。
- 原执行端已明确在启动前拒绝、经人工确认未扣款且未开通的失败，可由 ID 侧按原回执批准一次重新受理。查询保留旧记录并显示重试入口；客户需重新验码、提供最新账号资料并主动提交。商城仍按原店铺、原回执和提交版本受理，旧回执不能解除新一次提交的待核对状态。
- 执行端暂时查不到任务，也不能清除网站已有的不确定提交状态。查询仍显示待核对；待核对交易需由授权人员核对原任务。
- 已关闭服务／已下架入口的历史任务继续允许持原兑换码查询。客户查看完整目标邮箱；查询不返回供应商、支付资料、截图、执行日志或原始错误。

## 会话与安全

完整会话只经过服务端转发，不进入 Vendure 数据库、公共查询缓存或浏览器持久存储。ID 侧按现有加密、审计和事务规则处理；仅新增网站来源的终态任务 24 小时后清除会话，待核对任务按创建时间最多保留 7 天。清除会话不清除兑换码绑定、任务锁或交易证据。

公开操作分别限流，专用执行接口同时要求独立凭证与来源限制。生产还需确认可信代理和边缘限流；应用内限流为每进程窗口，不应把 CORS 当作鉴权。

## 本地联调复现

先在 ID 项目执行 API 类型检查和 API 构建，并等待构建成功退出，再从商城项目的 `packages/store-management-plugin` 运行：

```sh
GPT_RECHARGE_ID_PROJECT='/absolute/path/to/ID-project' bunx vitest run --config e2e/gpt-recharge.vitest.config.mts
```

该检查使用实际商城接口客户端、响应解析、GraphQL schema／resolver、转接服务、SQL.js 回执迁移及 ID 系统 Nest HTTP 控制器／拦截器／任务服务／任务仓库。ID 数据层用内存适配器，监听地址仅为本机随机端口，不启动整套 ID 网站、真实数据库或执行器。测试凭证全部为明确的合成资料。

本地链路验证不代替生产 MySQL 迁移、真实执行器、第三方渠道到账或实际订阅变更验收。最后状态、检查记录及剩余发布事项见 `docs/local-validation/gpt-recharge-20261016/integration/`。
