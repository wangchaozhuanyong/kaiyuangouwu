# 订单邮件策略与隔离闭环验收（2026-10-26）

本记录描述本次代码与隔离验收；正式提交、CI、生产部署、线上版本和外部收信结果分别记录，不以本地通过代替外部送达或实际扣款。

## 用户要求与最终规则

- 客户订单邮件仅用于明确选择邮箱收货的交付。普通下单／付款确认邮件停止发送，实物、混合和数字订单均适用。
- 人工交付任务刚创建、等待处理、只保存草稿时不发邮件；成品完整发布后才发送安全领取入口。
- 卡池缺货、分配不足、过期任务和已完成的旧发送任务不再次发送；只有当前可交付份数齐备的待发送／重试任务可以通知。
- 收件人必须来自当前订单确认的 `deliveryEmail`，不回退到登录邮箱或历史收件人。历史领取内容仍可按原授权访问。
- 旧确认邮件及不再就绪的通知由发送策略跳过，不产生“发送成功”或“发送失败”的业务回执。权限、领取资格撤销、失效链接、错误收件人等真实错误继续抛出，未改成成功或吞掉。
- 注册验证、找回密码、修改邮箱等账户邮件保持原流程。布局、内容、商品、价格、支付规则、服务端权限和数据库结构不变。

## 根因与代码范围

1. 普通订单确认与交付就绪通知是独立入口，旧规则仍允许实物和混合订单发送普通确认；待发队列也可能保留旧确认消息。`order-confirmation-email.ts` 停止新确认，`manual-delivery-email-guard.ts` 在每次处理时消费旧确认，并重新核对真实交付状态。
2. `EmailProcessor` 原先忽略发送策略的返回值，且先渲染模板，再执行策略。现在只有明确返回 `false` 才跳过，并在模板渲染及传输配置读取之前判断，使旧模板不存在时也能正确消费已过期消息；其他错误保留正常失败回执。
3. 自动发卡曾可回退到账户邮箱；人工通知可使用历史收件人。两项通知服务现在复用既有邮箱校验，只读取当前确认邮箱，并分别核对分配数量、成品内容、状态和领取资格。
4. 原 `dev-config.ts` 内两个交付 handler 原样提取到 `digital-delivery-email-handlers.ts`，生产配置与端到端测试调用同一工厂。没有另写通知业务来替代测试对象。

业务文件：`packages/commerce-fulfillment-plugin/src/{auto-card.service,manual-digital-delivery.service,customer-delivery-email.service}.ts`、`packages/email-plugin/src/{email-processor,types}.ts`、`packages/dev-server/{order-confirmation-email,manual-delivery-email-guard,digital-delivery-email-handlers,dev-config}.ts`。其余为对应 spec、既有数字闭环 E2E、测试配置、回环 SMTP 接收端及本记录。

## 实际闭环链路与边界

新增用例使用真实本地 HTTP GraphQL、Core 订单与支付状态机、MySQL、交付服务、生产同一 handler、EmailPlugin、SQL JobRecord 队列、EmailProcessor、MJML／Handlebars、Nodemailer、SMTP 协议和领取 API。支付提供方回执及数据是合成夹具；SMTP 只绑定 `127.0.0.1`，不向外转发。

混合订单付款后，确认邮件和交付邮件均未处理；人工成品发布后实际收到一封 MIME 邮件，收件人为显式确认、且不同于账户邮箱的地址。邮件只有安全入口，没有成品密码。按浏览器 HTML 解析规则取得链接，真实 token 校验及领取通过；先读取不记领取，重复领取保持幂等。卡密订单也只向所选邮箱通知并可领取。最后发布一条已不就绪的旧事件，实际处理器返回 false、不再发信；处理结果精确为 `[true, true, false]`，不靠重试掩盖事务问题。

首次 SQLjs 验收发现既有十进制驱动数值／字符串差异及测试端没有解码 HTML 实体；保留记录，采用生产 MySQL，并用既有 JSDOM 读取真实 href，保持原 URL／订单／token 断言。首次内存队列虽通过 15 项，但有提交前读不到交付记录的瞬时错误，未将它作为最终队列验收；改用生产同款 SQL 队列，在同一事务持久化意图、提交后发送，最终两轮 SQL 队列均 15 项通过。最后一轮包含最终授权、模板前策略及不同收件人修复。

这些证据证明隔离条件下的软件闭环，不证明真实资金移动、第三方账号使用、外部支付服务商沙箱、生产 SMTP／TLS 或 Gmail／Outlook／国内邮箱实收。外部收信需要可用的正式运维会话，尚未发送外部测试邮件；未用生产订单或主网付款代替测试。
