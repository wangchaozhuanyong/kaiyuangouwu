# Storefront first-view image loading review (2026-09-25)

Status: local candidate verified; production improvement is not yet measured or released.

## Latest local candidate observation

After the three-window candidate was rebuilt, a 1440 px anonymous local preview using the public Shop API showed 11 flash-sale products and no document overflow. In one cold visit the first hero image became ready about 5.9 seconds after navigation; the hero request began around 2.05 seconds, while the current public Asset Server still rejected the new `storefront-hero-fit-*` variant and `SafeImage` fell back to the original PNG. This Vite preview does not expand the production Nginx SSI preload. A separate anonymous Chromium navigation directly to the live site timed out before its page scripts mounted, so it cannot supply a valid live LCP comparison. A read-only HTML response did contain one preload for the currently deployed legacy hero preset.

The loaded real-store banner also exposed a visual issue independent of the request delay: a light merchant palette set dark headline and body text on the `HeroScene` child, while the image gradient was drawn on its parent and therefore used a dark fallback. The shared gradient now lives on the image link inside the same configured scope as the copy. The formal preview screenshot `formal-public-hero-contrast-fixed-1440.png` shows readable on-image copy; `formal-public-hero-contrast-mobile-390.png` confirms the mobile image and copy retain their stacked layout. This fixes the palette mismatch, not the old server's preset 400 or production image timing.

The same real-store preview exposed a second fallback issue on large story artwork. When the old Asset Server rejected a responsive hero preset, `SafeImage` disabled responsive sources and also dropped its small placeholder URL. The frame then showed an empty fallback while the original image was still loading. The shared component now derives the hero placeholder from the original asset independently of the responsive request state. A targeted 25/25 image test run and a deterministic browser check confirmed that the placeholder stays visible through a preset failure and the original image can replace it afterward. The browser capture is `formal-story-fallback-placeholder-1440.png`. This improves the waiting state; the server preset update and real-network timing remain release gates.

## Observed production baseline

A read-only, anonymous Chromium visit to the public homepage at 1440 and 390 px showed that the first large image request completed before its image element appeared. In one cold sample, first contentful paint was about 0.56/0.69 seconds and the first large visible image was ready about 1.59/2.75 seconds after navigation (desktop/mobile). In another sample the hero asset request finished near 0.51/0.58 seconds while the visible hero image appeared about 2.07/2.34 seconds after navigation. These are individual lab samples, not field LCP percentiles.

The Shop API waterfall explains the gap: configuration establishes the current host's store, then content and catalog requests start. A mobile sample returned homepage content around 2.6 seconds and the general product list around 3.66 seconds. The old `HomePage` loading prop waited for both, so an already downloaded hero still stayed behind the whole-page skeleton until products arrived. Other visible images were ready after three seconds; many images outside the viewport were intentionally lazy and should not be counted as broken.

A further anonymous cold sample on 2026-09-25 returned homepage content at about 4.7 seconds on desktop and 2.7 seconds on mobile; the hero element appeared just after that response. The same visit fetched both a responsive hero and a separate original PNG of about 1.8 MB. The image endpoint returned `public, max-age=14400, s-maxage=300, must-revalidate`; cache headers alone do not explain this wait. These results are still one-off lab timings, and the deployed bundle differs from this candidate.

A later anonymous 390 px sample recorded GraphQL operation names and response timings in `packages/storefront/artifacts/readiness/current-live-shop-api-mobile-waterfall.json`: `StorefrontConfig` took 331 ms, `StorefrontContent` 305 ms after config, while the first `StorefrontCatalog` took 2,376 ms. Another catalog request was cancelled and restarted. This single visit supports keeping homepage artwork independent from the catalog response; it does not establish a stable backend bottleneck or prove why the catalog request restarted. Do not infer a need for server rendering from this sample alone.

## Candidate behavior

- Keep configuration as the store identity gate. Do not speculatively fetch content for the build's fallback market: in a multi-store test that produced a second content request after the actual store was resolved.
- Show the homepage when its configured content resolves. The catalog continues loading independently. The product area shows a scoped loading state, then products, a real empty state, or a retryable error. Category and other catalog-dependent pages retain their existing loading conditions.
- Preserve the existing shared `SafeImage` candidate verification, responsive sources, first-view preload, dimensions, and asset cache rules. No replacement store image or guessed product is substituted for unpublished content.

With a synthetic product response delayed 1.5 seconds, the updated production bundle displayed its large hero image at about 0.42 seconds on desktop and 0.36 seconds on mobile, before the product response in both cases. This demonstrates the dependency split, not a promise of equivalent timings on the public network. `HomePage` has regression tests for both layouts while products remain pending or fail. In the updated production bundle, 390 and 1440 px browser checks showed that a failed product request retained the hero, displayed a retryable product error instead of a false empty state, and recovered after retry. Full storefront unit tests (146 files, 1165 tests) and the direct production build passed in the clean dependency checkout.

The candidate browser check now confirms that the homepage requests only the responsive hero candidate. On the authentication pages, image contrast sampling now reads the displayed, decoded `SafeImage` element instead of downloading the managed original again. A shared image-ready callback covers images decoded from cache as well as normal load events. The mobile layout hides the login and registration hero, so both route-level preload paths and the image component now skip it below 1024 px. The 390 and 1440 px fixture check covered six home/login/register states: mobile authentication requested no artwork; desktop authentication and both home states requested only their responsive candidates, with no original asset. Resizing mobile login to desktop fetched its image once, and resizing back removed it. The light same-origin test image selected direct contrast. The relevant 50 unit tests passed before the final route-boundary adjustment; its affected 36 tests, storefront TypeScript check, and production build passed afterward in the clean dependency checkout. Three skins × login/register × mobile/desktop also passed 12 visual checks. This does not establish the public site's behavior until its matching backend and frontend are released together.

## Release acceptance still required

### Full-width managed artwork rollout

The current DAMATONG Shop API reports three hero assets at 2200×715. The candidate reads `imageAsset.width/height` from the Shop API, reserves that ratio in the formal desktop hero, and requests `storefront-hero-fit-*` variants. A read-only public Shop API probe confirmed that the current schema returns asset dimensions. The existing production Asset Server does not yet register these new variant names. In the local candidate preview proxied to that server, a hero fit request returned HTTP 400 `Invalid parameters`; `SafeImage` then loaded the full original PNG. This confirms that frontend-first rollout would retain the visible late image reveal. The hero placeholder now also uses `resize/inside`; a 1600×520 sample produces a 64×21 WebP rather than a cropped 64×32 preview.

Release the Asset Server preset configuration before the storefront bundle that references it. After the server update, verify all four hero widths and the low-resolution placeholder return WebP with the original aspect ratio and cacheable responses. Then verify the storefront at desktop and mobile widths requests the expected candidate once, does not also request the original PNG, and shows the same composition before and after decoding. Repeat cold and warm LCP checks with real store artwork and constrained mobile bandwidth. Local fixture and the current production proxy cannot prove these release measurements.

A local HTTP probe against the candidate Asset Server and its actual `storefrontAssetPresets` now covers the current store's reported 2200×715 ratio. The four fit variants returned WebP at 480×156, 960×312, 1440×468, and 1600×520; the wide placeholder returned 64×21. A repeat request returned identical cached bytes for all five. The legacy `storefront-hero-960` still returned its 960×480 crop, so an older storefront bundle can continue using it while the backend is updated. The repeatable probe is `packages/storefront/artifacts/readiness/asset-preset-http-probe.ts` (6/6 HTTP cases). It uses a synthetic image and the preset strategy without a store authorization lookup, so real-store access and the public cache header remain release acceptance checks.

### Candidate with the current public Shop API

The candidate's new announcement `createdAt` selection was rejected by the current production schema with HTTP 400, which made the whole homepage content unavailable. The content client now retries that specific older schema without `createdAt` while retaining flash sales, announcements, branding, and page blocks. It still uses `createdAt` when the new backend provides it. The API/home targeted tests (159), TypeScript, ESLint, and the production storefront build passed.

An anonymous, read-only local preview of the rebuilt candidate proxied the real public Shop API and asset URLs. In one desktop/mobile cold visit, the first hero image was ready at 3.23/2.73 seconds; the content response completed at 3.05/2.60 seconds. The compatibility retry was visible as one expected 400 followed by 200. In the same browser tabs, refresh restored public content from session storage and the cached hero appeared at 0.66/0.43 seconds, without another content request. The corresponding measurements are in `packages/storefront/artifacts/readiness/current-335-live-candidate-refresh-probe.json`, with 1440/390 px screenshots in the same directory. A separate new-tab sample reused the network cache but not tab-scoped session storage; it is not a refresh measurement.

These are individual local-proxy measurements, not production LCP or proof of consistently fast cold visits. Current cold visits still depend on store configuration and content API latency. The deployed backend does not yet expose announcement `createdAt`, so the retry adds one network round trip until both sides of the release match. Keep the old-schema retry for rolling deployment; remove it only after every supported backend provides the field. A host-scoped server bootstrap is the next architectural option if the content API remains the dominant cold-visit delay after deployment and real-user measurement.

### Homepage request priority check

Three anonymous public GraphQL rounds returned the storefront content field alone in about 0.13–0.24 seconds and the combined content, sale, announcement and settings query in about 0.26–0.80 seconds. These short samples suggest that data grouping and concurrent requests can delay the hero, but they do not isolate one stable server bottleneck. A browser experiment that held nonessential queries for two seconds also showed variable cold hero timings, so it is not a reliable performance benchmark.

The candidate previously started two home merchandising catalog requests before homepage content existed, including on unrelated pages. They now wait for resolved content and run only on the home page; the recommendations route keeps its own catalog request. A real public API browser check saw both home catalog requests start after the content response, only one category catalog request on `/category`, and only the recommendations catalog request on `/recommendations`. No page errors were seen. One subsequent 390 px hero asset took 2.3 seconds through the local proxy, but six direct requests for the same 132,500-byte cached WebP took 36–243 ms, so this does not establish a persistent asset-server delay. Evidence is in `packages/storefront/artifacts/readiness/current-333-public-content-field-timing.json`, `current-333-content-priority-probe.json`, `current-335-home-merch-priority-after.json`, `current-335-merch-route-check.json`, and `current-335-public-hero-asset-timing.json`. Request ordering is verified; a consistent cold-load speedup is not yet proven.

### First carousel image before the next image

The carousel previously started decoding the next managed hero immediately after mount, so the first and second full-size hero requests could compete during a cold visit. It now waits for the visible `SafeImage` to finish decoding before it prefetches the next slide. Manual selection and autoplay continue to decode the destination image before changing slides, and data-saver rules still disable speculative prefetch.

The repeatable local image-loading browser script now uses two managed hero images and a delayed first full-size response. At 390 and 1440 px, the next full-size request started only after the first full-size request finished; the small placeholder request remains separate. The script also passed home, login and registration behavior in both widths (six states), while the relevant homepage/carousel unit tests passed 66/66 and the production storefront build passed. A later live-proxy run stalled before Shop API responses, while a direct API probe returned normally; that run cannot verify real-site carousel timing or be treated as a frontend failure. Evidence is in `packages/storefront/artifacts/readiness/current-336-hero-prefetch-fixture-v2.json` and `packages/storefront/e2e/image-loading/verify.mjs`.

The six-state check was rerun against the current local production preview on 2026-09-25 and passed. The second full-size hero request started 10 ms after the first completed at 390 px and 29 ms after at 1440 px. Mobile login and registration made no hidden artwork request; desktop made one responsive request each. The recorded output is `packages/storefront/artifacts/readiness/current-338-image-loading-fixture.json`; the six states also passed after the latest local storefront rebuild in `current-final-image-loading-fixture.json`. This remains fixture evidence, not a public-site performance measurement.

After an authorized release, measure real-user LCP, image element insertion time, image request completion, and Shop API configuration/content/product timings by store and viewport. Check cold and warm visits, constrained mobile bandwidth, active promotional artwork, cache HIT/MISS, and failures. The candidate cannot prove production improvement before deployment. If the content request remains the dominant delay, the next architectural step is a host-scoped bootstrap or server render that carries the verified store, language, currency, and hero metadata into initial HTML. That change needs a separate design and release review; shipping a guessed tenant image from a static bundle would violate multi-store correctness.
